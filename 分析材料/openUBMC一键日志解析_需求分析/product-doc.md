# openUBMC 一键日志解析（bmcstudio-log-reviewer）· 产品文档

## 技术栈概览

纯 Node.js（零运行时依赖，README 原文）+ TypeScript 编译产物 + Vue3 前端（webview）。VS Code / openUBMC Studio 扩展形态，`extensionKind: ["workspace","ui"]`，跨平台（macOS/Windows/Linux 随 Studio）。数据源是 openUBMC 服务器导出的"一键日志 dump"——文本日志、CSV、MDB 属性快照、`.gz` 压缩包的混合体，无需起 HTTP 服务、无需浏览器，在 IDE 内直接渲染。额外暴露 7 个 MCP 工具，可被外部 AI Agent 调用做深度诊断。许可证 MulanPSL-2.0，发布方 `openubmc`（华为系开源社区），仓库 `gitcode.com/openUBMC/bmcstudio_log_reviewer`。

## 一键日志解析（唯一功能模块）

> 本产品体量与边界清晰，17 个数据域 + 1 套诊断能力共享同一入口、同一数据源、同一使用场景，不构成需要拆分的多个独立模块（不满足"独立子目录/独立 WebView/使用场景完全不同"任一判据），按单模块展开 A–H。

### 需求背景

openUBMC 服务器现场故障排查时，工程师用"一键日志采集"命令导出一个压缩包，内含数十个文本/CSV/二进制文件（SEL 事件、MDB 属性快照、操作日志、性能采样、传感器数据等）。在本扩展出现前，排查这份 dump 需要手工用文本编辑器/脚本逐个打开、跨文件比对——本扩展把这个过程压缩成"选中压缩包 → Studio 内直接看到结构化可视化页面"一步，并额外接入 AI Agent 做跨文件根因分析。

### 功能定义

一句话：给 openUBMC 现场排障工程师用的、**在 IDE 内一步打开一键日志 dump 并做可视化 + 双层诊断（本地规则 + 可选的 AI Agent RAG 诊断）**的工具，替代"手工打开一堆文本/CSV/MDB 文件逐个比对"的排查方式。

核心能力清单：
1. Dump 打开与自动定位（压缩包自动解压 / 目录自动找 `AppDump`）
2. 17 个业务域可视化（概览、FRU/版本、告警/传感器、操作日志、性能、调速、功率/温度、CSR、线缆、丝印、系统日志…）
3. 规则版本地诊断（仅操作失败类，见 business-logic.md）
4. Agent 深度诊断（MCP 驱动，RAG 校准，流式产出可信 Issue）
5. PDF 报告导出（分析完成后解锁）
6. 最近打开历史（侧边栏 + MCP 可查）

### 使用场景

1. **客户现场故障复现后的远程排查**：客户报障 → 现场采集一键日志包 → 通过内部渠道传给 BMC 工程师 → 工程师在 Studio 里打开压缩包，先看"概览"页确认健康态与关键告警，再切到"操作日志"确认最近一次失败操作，触发 AI Agent 深度诊断，等待 Issue 流式产出，导出 PDF 附到工单里回复客户。
2. **版本升级前后的对比巡检**：工程师对同一台设备升级前后各采一次 dump，分别打开对比"性能""调速""功率"几个 tab，人工判断有无回归——这个场景当前完全靠肉眼对比两次分别打开的结果，**没有内置的"对比模式"**（待确认清单里的一个潜在机会点）。
3. **新功能验证阶段的自测**：BMC 固件开发工程师本地跑通某个流程后主动"一键日志"导出，打开本扩展快速确认各业务域数据是否符合预期，而不是逐个查看原始 MDB/CSV。
4. **AI Agent 自动化巡检**（新场景，本产品独有）：MCP 客户端（如 CI 流程里挂载的 Agent，或工程师在对话式界面里直接问"这份 dump 有什么问题"）无需人工打开 UI，直接调用 `log_reviewer_diagnose`/`get_section` 拿到数据，走 RAG 校准链路产出 Issue，最终工程师只看 Agent 汇总结论。

### 用户痛点

1. **散落多格式文件手工比对**——README 明确点名的核心痛点，本产品用统一可视化直接解决。
2. **规则诊断覆盖面窄且不透明**——0 条告警异常在当前 UI 上无法区分"真扫描过没问题"与"这类扫描根本没开"，属于信任风险，非单纯体验问题。
3. **跨文件根因关联依赖经验**——本产品用±5min 时间窗关联自动化解决了"操作失败"这一类，但告警/性能类的跨文件关联仍未启用（规则版）或完全依赖 Agent 是否可用（智能体版）。

### 核心操作流程

```
① 打开 dump（压缩包或目录，二选一）——必须先完成，其余步骤都依赖已解析的 dumpDir
   ├─ 可任意顺序：② 浏览各业务域 tab（概览/FRU/告警/性能/调速/…）
   └─ ③ 触发智能诊断（可选，依赖 MCP Agent 是否接入；若接入则走④⑤，否则只能看②里的规则版 detection tab）
④ Agent 收集证据（get_section/diagnose，顺序不限）
⑤ Agent 流式产出 Issue（upsert_issue，同一 issueId 内部 revision 必须递增）
⑥ Agent 调用 complete → TopN 快照固化 → PDF 导出解锁（⑥依赖⑤已产出至少部分 Issue，但代码层面未见"Issue 数=0 时禁止 complete"的强校验，属待确认项）
```

### 数据结构概览

详见 `data-structure.md`，摘要：核心实体是 Dump 目录（`AppDump`+`LogDump`+MDB 快照）、GenericInfo/ProductInfo（多为 MDB 三段式查询 + 定宽文本解析）、DetectionItem（规则版，覆盖窄）、FaultDiag（原始证据透传）、Issue（Agent 产出，schema 强约束 evidence+ragAssessment）、机型 Profile（策略模式，当前仅 BC83+通用兜底）。

#### 特殊技术概念说明：MDB 属性快照（非 Access 数据库）

*① 它是什么？* 一种把 openUBMC 组件运行时的属性值"拍快照"导出成纯文本的格式——按"模块名/对象路径/属性名"三段式组织，本质是一份对象属性表的文本序列化，与微软 Access 的 `.mdb` 数据库文件**同名不同物**。
*② 为什么这样设计？* openUBMC 内部用 MDB（对象属性管理）做组件间状态同步，一键日志采集时直接把这棵属性树 dump 成文本，比为每个业务域单独设计导出格式更省事、更能保证"看到的就是运行时真实状态"。
*③ 它具体怎么工作？*
```
文本快照结构（简化示意，按对象路径分组，空行分隔）：
[/bmc/kepler/Systems/1/Product]
ProductName = "TaiShan 200"
SerialNumber = "2102313XSB10P5100233"

[EthernetInterfaces]
Mac = "xx:xx:xx:xx:xx:xx"

读取方式：mdbGetFirst(base, '模块名', '/对象/路径', '属性名') → 逐行扫描匹配、
取该属性第一次出现的值，遇到空行则重置当前对象上下文
```
*④ 对设计意味着什么？* UI 不应假设某个属性一定有值（三段式查询可能查不到，代码普遍用 `|| 默认值` 兜底）；"默认值兜底"与"MDB 里确实是这个值"在当前数据里不可区分，UI 层如果要提高可信度，需要产品/后端补一个"是否命中/是否兜底"的标志位（写入待确认清单）。

### 设计机会点

| # | 机会点 | 当前痛点 | 建议方向 | 实现层级 | 商业权重 |
|---|--------|---------|---------|:---:|:---:|

**三列流视图（痛点 → 洞察 → 策略）**：

| 用户痛点 | 洞察汇聚 | 设计策略 |
|---------|---------|---------|
| P1 散落多格式文件手工比对 | **翻译比查找更高频**——真正费时的不是"文件在哪"，而是"这个字段/日志行是什么意思、和别的文件有什么关系" | 统一可视化 + 跨文件时间窗关联（已实现的规则版是这条洞察的具体落地） |
| P2 规则诊断覆盖窄且不透明 | **"看起来智能"比"真的智能"更容易被过度信任**——AI/自动化功能一旦上线，用户默认它是全面的，覆盖缺口不主动声明就是欺骗性设计 | E1 状态条 + E7 机型透明化：任何"自动扫描/自动识别"类结果都必须自带覆盖范围/置信来源说明 |
| P3 跨文件根因关联依赖经验 | **可信的自动化诊断需要可验证的证据链，而不是更聪明的模型**——本产品用 schema 强制 evidence 原文引用，说明维护团队已经认同这条洞察 | E2 证据追溯面板：把已经在协议层做对的事（强制证据）在 UI 层同等重视地呈现出来 |

### 专利潜力评估

- **组合关键词**：「IDE 内嵌可视化」×「本地规则诊断 + MCP Agent 分层诊断」×「Schema 强制原文证据 + 知识库范围锁定的 AI 诊断结果提交协议」
- 差异化点不在单项能力（RAG 诊断、IDE 插件都不新鲜），而在**这三者的组合**：把"AI 结论必须附带可验证证据、且证据来源被协议锁定在专用知识库"做成一个可复用的 MCP 工具 schema，而非一次性的 prompt 约束。
- 行业先例：【推断·待确认（因无外部访问，无法确认是否已有同类"MCP 工具 schema 级强制证据引用"的公开先例）】
- 评级：**中**——组合较新颖，但"要求 AI 附证据"这个单项思路本身在 AI 应用领域已不算稀缺，需要外部核实是否已有类似 schema 化实现才能判断是否够到"高"。

**专利描述原则示例**（仅从交互角度描述，不引用实现技术）：
✓ 正确描述："用户发起一次智能诊断后，系统展示的每一条问题结论都附带其判断依据的原始记录片段与知识库引用来源，且这些依据被限定在一个专门维护的故障案例范围内产生，用户可展开查看每条依据而非仅看结论文字。"
✗ 错误描述："使用 JSON Schema 的 minItems 强制 evidence 数组非空。"

### 设计注意事项

1. **诚实呈现诊断覆盖范围是本产品最大的设计红线**——规则版 `0` 条告警/性能异常和"未启用"在当前后端返回结构下不可区分，任何 UI 呈现如果没有显式覆盖范围说明，都构成对现场判断的潜在误导（技术约束→设计红线，见 E1）。
2. `GenericInfo` 里 `PowerState`/`IndicatorLEDState`/`FanSupported`/`KVMSupported` 是硬编码占位值，不是真实读数——UI 不应把它们当作可信状态展示，或至少不能用它们做任何条件判断（如"因为 FanSupported=true 所以显示风扇 tab"这类逻辑是危险的，因为它对所有机型恒真）。
3. 定宽文本解析（`firmware_mgmt_info.txt`）对格式变化零容错，上游格式一旦变化会静默产出错位数据，属于工程侧需要防御性校验的技术债，设计侧应预留"数据看起来异常时"的降级展示（而非假设后端数据永远干净）。
4. `revision` 递增校验、`topN` 用户主权覆盖 Agent 建议这两条规则，是"后端设计已经做对但可能未在前端呈现"的例子——设计工作的一部分是把已经存在的正确后端行为，用用户能感知到的方式表达出来（而不是用户完全无感知这些规则在起作用）。
5. 机型 Profile 目前只有 1 个具体机型（BC83），"多机型支持"是架构承诺、非当前已验证事实——面向非 BC83 机型的用户，设计上应避免暗示"已针对你的机型做了专门适配"。
