CONCEPT · 概念解析

MDB 属性快照 —— 不是 Access 数据库

① 它是什么

openUBMC 组件运行时属性的纯文本"快照"导出，按「模块名 / 对象路径 / 属性名」三段式组织。与微软 Access 的 .mdb 数据库文件同名不同物。

③ 怎么工作（真实读取代码）

// mdbGetFirst(base, module, objectPath, prop) mdbGetFirst(base, 'event', 'Events', 'Health') mdbGetFirst(base, 'product_mgmt', '/bmc/kepler/Systems/1/Product', 'ProductName')

逐行扫描匹配对象路径块，取该属性第一次出现的值；空行重置当前对象上下文。取值类型强制转换：加引号字符串→去引号，true/false→boolean，纯数字→Number。

② 为什么这样设计

组件状态同步本就靠属性树，采集时直接把这棵树 dump 成文本，比为每个业务域单独设计导出格式更省事，也保证"看到的就是运行时真实状态"。

④ 对设计意味着什么

  • UI 不应假设属性一定有值——多数字段有 || 默认值 兜底
  • 兜底值与"MDB 里真实读到"当前不可区分
  • 提高可信度需要产品/后端补一个命中标志位
SCENARIO · 使用场景

四个典型使用场景

① 客户现场故障远程排查

客户报障 → 现场采一键日志包 → 传给 BMC 工程师 → Studio 内打开，先看概览确认健康态，切到操作日志确认最近失败，触发 AI 诊断，导出 PDF 附到工单回复客户。

② 版本升级前后对比巡检

升级前后各采一次 dump，分别打开对比性能/调速/功率，人工判断有无回归——当前无内置对比模式，完全靠肉眼对比两个窗口。

③ 新功能验证自测

固件工程师本地跑通流程后主动导出一键日志，打开本扩展快速确认各业务域数据符合预期，替代逐个查看原始 MDB/CSV。

④ AI Agent 自动化巡检（产品独有）

MCP 客户端无需人工打开 UI，直接调用 get_section/diagnose 拿数据，走 RAG 校准链路产出 Issue，工程师只看 Agent 汇总结论。

PAIN · 痛点分析

三条核心痛点

P1 · 散落多格式文件手工比对

README 原文点名的核心痛点："原本散落在一堆文本、CSV、MDB dump 和 .gz 里的…信息"。
痛点核心：信息密度分散在多种格式，人工比对耗时且易漏。

P2 · 规则诊断覆盖窄且不透明

源码逐字证据：assertedN=0 / perfN=0 恒定，告警与性能扫描代码路径被注释标注"accuracy insufficient"而关闭。
痛点核心："0 条异常"与"扫描未启用"当前完全不可区分，构成信任风险。

P3 · 跨文件根因关联依赖经验

规则版 _inferFailureCause 的存在本身就是证据——三级降级查找算法正是为了自动化这个人工比对过程。
痛点核心：没有工具前，时间上相邻但文件不同的关联证据全靠工程师记忆串联。
