# openUBMC 一键日志解析 · UI 设计优化简报

> **模式判断：优化模式**。`preview/index.html`（=已提交进 BMC-01 IDE 的 `web-app/public/log-reviewer.html`）已经是一版可用的高保真 Demo，视觉上已经遵循了 BMC-01 项目的 PTO 派生设计系统。但它是在**没有读到 vsix 源码真实业务逻辑**的情况下、凭对"日志查看器该有什么"的通用想象搭的——本次深挖 vsix 源码后发现的关键事实（规则版诊断覆盖窄、Agent 诊断的证据链设计、TopN 用户主权、机型 Profile 单一）在这版 Demo 里完全没有体现，尤其是「智能诊断」tab，是本次优化的核心对象。

你是一位专注于工程工具（Developer Tools / 现场诊断工具）领域的 UI 设计师。
- 产品：openUBMC 一键日志解析——面向 BMC 固件工程师/现场技术支持的 IDE 内嵌日志可视化 + 双层智能诊断工具
- 整体配色：背景 `#101010`，主强调色 `#0077FF`，文字 `rgba(255,255,255,.90)`
- 风格参照：VS Code / JetBrains 风格——高信息密度、功能优先、暗色系
- 目标用户：BMC 固件工程师/FAE，习惯 VS Code / Studio 风格 IDE，能读懂十六进制、日志格式、专业术语

## §A 设计系统（委托）

**设计系统 = BMC-01 项目内置 PTO 派生 design token 集**；定义见仓库 `CLAUDE.md`「欢迎系页面视觉规范」一节 + `web-app/src/styles/ide-frame.css`。生成/修改 Demo 时：
- 所有颜色用其语义 token：`--background #101010` / `--surface-1 #161616` / `--surface-2 #1c1c1c` / `--surface-3 #262626` / `--primary #0077FF` / `--success #04d793` / `--accent-purple #a78bfa`（AI/agent 相关一律用这个紫色 + ✦ 四角星面型图标）；文字 `rgba(255,255,255,.90/.60/.40)`。
- 按钮/chip/输入框圆角只允许 `100px`/`999px`（胶囊），卡片 `16px`。
- 禁止新增描边（每页面 ≤2 处 1px 白色描边），一律用 `--surface-*`/`rgba(255,255,255,.06)` 填充分层。
- 每个独立 HTML 页面必须自带深色滚动条规则（`::-webkit-scrollbar` 全套）——`preview/index.html` 已包含，改动时不要删除。
- 不发明新配色，尤其**不得使用**私造 indigo/violet（`#4369ef` `#4F46E5` `#5b8af5` `#6159ef` `#7c3aed` `#8b5cf6` `#6366f1`）与私造绿色（只允许 `#04d793`）。

能力规格（下方 §B/§C）保持视觉无关——换设计系统只需重写本节。

## §B 当前 UI 问题诊断（逐组件，可量化）

### 首用 30 秒走查（「智能诊断」tab，五镜逐镜）

| 镜 | 检查什么 | 结论 |
|----|---------|------|
| 镜1 首屏与空态 | 「智能诊断」tab 首屏空白率 | **通过**——两张 card 铺满，无明显空白，但内容是静态占位文字，不是"可操作示例" |
| 镜2 可扫读性 | 提示文字/操作符是否堆挤 | **通过**（本 tab 无大量操作符堆叠场景） |
| 镜3 空间叙事 | 宽屏内容孤岛、操作区与反馈区是否并排 | **B1 Finding**：诊断结论卡（`.diag-item`）单栏纵向堆叠，无"证据/来源"侧栏，宽屏下右侧无内容，未按数据实际结构（Issue 含 evidence[]/ragAssessment）设计双栏 |
| 镜4 数据流可视化 | 多阶段处理是否画出数据流动 | **B2 Finding**：规则版三级降级查找（模块名→别名→全局 ±5min）与 Agent 诊断（收集证据→RAG 校准→产出 Issue）都是有明确阶段的处理链路，当前 UI 完全不可见，用户看不出"这个结论是怎么来的" |
| 镜5 结果状态编码 | 批量结果可否扫读出全局结论 | **B3 Finding**：三条诊断卡片用 `tag-warn`/`tag-info`/`tag-bad` 三色标签，但没有顶部"覆盖范围/置信度"摘要，且这三条是纯占位文案，未体现真实的 `severity`（critical/high/medium/low）、`urgency`（0–100）、`confidence`（0–1）三个独立字段 |

### 「智能诊断」tab 逐组件问题

| 维度 | 组件 / 位置 | 当前状态（可量化） | 优先级 |
|------|-----------|-----------------|--------|
| 信息完整性 | 诊断结论卡（`.diag-item`） | 只有 title + p 描述，无 `evidence`（原文引用）与 `ragAssessment.references`（知识库来源）——真实数据结构里这两项是 Issue 的 schema 强制字段，UI 完全没有承接 | 🔴 |
| 信息完整性 | 同上 | 无 `severity`(4级枚举)/`urgency`(0-100)/`confidence`(0-1) 三个独立维度的可视化，只有一个笼统的三色 tag | 🔴 |
| 可信度 | 整个「概览」/「告警与传感器」tab | `chip--warn`「健康状态：轻微告警」是硬编码演示态，未呈现"规则版诊断只覆盖操作失败类问题，告警/性能扫描当前未启用"这一关键事实——用户可能误以为"0 条告警扫描异常=已扫描且干净" | 🔴 |
| 可信度 | 「概览」tab 产品信息卡 | 无"识别机型：BC83 专用 Profile / 通用兜底"标识——真实产品架构上只有 1 个具体机型 Profile，其余机型走通用兜底，UI 未体现这个差异 | 🟡 |
| 一致性 | AI 智能诊断按钮 | 已正确使用紫色✦四角星（符合规范），但点击后仅 `postMessage` 派发终端命令，诊断 tab 内容本身不随之更新为"分析中→流式产出"状态，逻辑上诊断结果应该是流式到达的（`upsert_issue` 逐条回调），当前是一次性静态展示 | 🟡 |
| 状态覆盖 | PDF 导出 | 当前 Demo 完全没有 PDF 导出入口，而真实产品里"分析完成解锁 PDF 导出"是一个明确的状态转换点 | 🟡 |
| 布局 | 顶部 dump 概况条 | `hdr-dump` 固定展示一个演示文件名 + 机型 chip，无"未识别机型"或"多机型候选"的状态设计 | 🟢 |

## §C 问题 → 目标状态映射

### 「智能诊断」tab

**B1：诊断结论卡无证据/来源侧栏**
- 目标：诊断卡改为可展开结构——默认显示 `title` + `severity`(译中文：严重/高/中/低) + 顶部一行 `urgency`/`confidence` 双徽章；点击展开显示 `evidence[]`（每条含来源文件/位置 + 原文摘录，等宽字体、深色代码块底）与 `ragAssessment`（检索语句 + 命中的知识库片段列表，标注"仅检索故障案例库"）。〔服务于：FAE·现场排障时需要向客户/上级证明结论有据可查〕

**B2：多阶段处理链路不可见**
- 目标：诊断卡的 `cause` 字段用简短「链路条」呈现：`操作失败 → 关联 app.log (±5min) → N 条候选 → 去重后 M 种`，每段用小箭头连接、等宽字体，而非纯文字段落；Agent 版诊断展开态显示"证据收集 → RAG 校准（fault_cases）→ 结论产出"三步进度点（即使已完成也保留三步标记，帮助用户理解结论生成过程）。〔服务于：BMC 工程师·需要判断"这个结论可不可信、值不值得深挖"〕

**B3：severity/urgency/confidence 未分别可视化**
- 目标：每条诊断结论顶部一行三个独立元素——`severity` 用色彩标签（严重#ff4b7b/高#ffaa3b/中#0077FF/低灰）；`urgency` 用 0–100 的短进度条 + 数字；`confidence` 用 0–1 的百分比 + 淡色徽章；三者并排展示，不合并成一个笼统分数。〔服务于：工程师需要快速分拣"紧急但可能不准"vs"不紧急但很确定"两类问题〕

**B4：诊断覆盖范围不透明**
- 目标：「概览」与「告警与传感器」tab 顶部增加一条**始终可见**的覆盖范围说明条（非可关闭 toast，因为这是持续性的信任声明，不是一次性通知）："规则诊断当前覆盖：操作失败关联查找；告警断言扫描、性能异常扫描暂未启用"，用中性灰底 + 小图标，不是警示红/黄（这不是错误，是能力边界声明）。〔服务于：所有用户·避免把"未启用"误读为"已扫描无异常"〕

**B5：机型识别透明化**
- 目标：「概览」产品信息卡增加一行"匹配机型：BC83 专用解析 / 通用解析（未匹配到专用机型）"，用小 chip 展示，紫色（`#a78bfa`，与其它元数据区分）或中性灰（未匹配时）。〔服务于：非 BC83 机型用户·判断数据可信度〕

**B6：诊断状态非流式**
- 目标：点击「AI 智能诊断」后，「智能诊断」tab 切换为"进行中"态——顶部显示 3 步进度指示（收集证据/RAG 校准/生成结论），诊断卡以逐条淡入方式追加出现（模拟真实的 `upsert_issue` 流式回调），全部到达后显示"分析完成，可导出 PDF"。〔服务于：现场工程师·长耗时诊断需要过程反馈而非长时间空白等待〕

**B7：无 PDF 导出入口**
- 目标：诊断完成态在 tab 顶部出现"导出 PDF 报告"胶囊按钮（分析未完成前置灰不可点，hover 提示"分析完成后可导出"）。〔服务于：需要把结论带出 IDE、附到工单/邮件的场景〕

## §D 跨视图一致性约束

- **Section header**：延续 `preview/index.html` 已有的 `.card h3` 样式（`--foreground-muted`、11–12px、大写字母间距），不新增第二套标题样式
- **状态色语义统一**：`tag-ok`(#04d793)/`tag-warn`(#ffaa3b)/`tag-bad`(#ff4b7b)/`tag-info`(#0077FF) 四色语义在全部 tab（尤其新增的 severity 标签）保持一致映射，不为诊断 tab 单独发明新配色
- **等宽字体**：所有证据摘录、事件码、字段值统一用 `var(--font-mono)`，与既有 `.mono` 类保持一致
- **覆盖范围声明条**的视觉语言（灰底、中性图标）需要与后续新增的其他"能力边界声明"场景复用同一套组件，不要每处单独设计
- **深浅主题**：本 Demo 全程实底 `#101010`，无渐变，遵循 CLAUDE.md「嵌入 IDE pane 的页面禁渐变」规则

## §E 各视图设计要求

### 智能诊断 tab（本轮唯一需要结构性改动的视图）

## §F 状态覆盖要求

| 状态 | 触发条件 | 视觉表现 |
|------|---------|---------|
| 初始/未分析 | 尚未点击「AI 智能诊断」 | 智能诊断 tab 显示引导卡 + 骨架预览（见 §E） |
| 分析中 | 点击后到 complete 前 | 3 步进度指示 + 已到达的诊断卡逐条淡入追加 |
| 分析完成 | complete 回调后 | 顶部小字"分析完成 · 共 N 条"+ 导出 PDF 按钮可点 |
| 分析失败 | 对应 `analysis_fail` | 顶部红色条显示失败原因文案，已产出的部分诊断卡保留可见 |
| 覆盖范围声明 | 常驻（非状态触发） | B4 灰底常驻条，不因用户交互消失 |
| 机型未匹配 | `model` 为 null 或非 BC83 | B5 chip 显示"通用解析"灰色变体，而非报错 |

## 明确不做的范围

- 不接真实 MCP/后端，Demo 阶段全部用 Mock 数据模拟流式效果
- 不做跨次 dump 对比模式（E4，机会点已记录但优先级 P2，超出本轮 Demo 范围）
- 不做规则版诊断算法本身的改进（E5，超出设计范围，需算法团队介入）
- 不做真实 PDF 生成，仅做入口与可用状态设计

## 待确认清单

1. 诊断卡展开态的证据摘录长度上限（原始 `excerpt` 可能很长，需要产品侧确认截断策略）
2. 「分析中」的 3 步进度是否需要精确对应真实 MCP 时序，还是仅作示意（本 Demo 按"示意"处理，工程阶段需要与真实回调对齐）
3. 覆盖范围声明条的文案措辞需要产品/技术团队最终确认（本简报草拟的"暂未启用"措辞可能需要更贴近对客户的正式表述）
